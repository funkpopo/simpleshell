# WebTerminal 大量历史内容性能排查

历史容量继续使用统一设置：默认 50,000 行，可配置到 500,000 行。输出仍由
xterm 保存和解析，只渲染可见屏幕；优化没有减少历史容量，也没有增加一份完整
历史文本副本。

本次确认并处理的开销：

- 提示符跟踪同时订阅逐行输出、重绘和解析完成事件。写入 50,000 行时产生约
  200,220 次附加行读取。现在主要在每批解析完成后跟踪一次，滚动和普通重绘
  不再重新识别提示符。超长逻辑行的识别最多回溯 32 行、读取 4,096 字符；
  超出后停止自动识别，输出内容仍完整保留。
- 开发/诊断模式的历史字节统计在容量达到上限后，每行调用数组 `shift()`，
  反复移动整个历史数组。现在使用环形队列，追加和淘汰为常数时间；修改容量
  时按顺序保留最新统计。
- 搜索插件扫描后，React hook 又在调用返回和搜索回调中分别遍历全部历史。
  现在只构建一个匹配位置索引，以目标 4 ms 的可取消任务片段扫描完整缓冲区。
  搜索输入合并 120 ms，输出更新合并 200 ms，跳转使用二分定位复用索引。
  计数不受高亮数量限制，视觉高亮最多 1,000 个单行装饰，当前匹配另行显示。
- 小段输出用动画帧调度写入，窗口隐藏或被遮挡时可能等待近一秒，且阻碍 ACK
  和背压恢复。现在按 8 ms 定时批处理，输出解析和 ACK 不依赖绘制帧。
- 链接悬停会拼接整个自动换行块。现在自动链接检测限制为 128 行、16,384
  字符；超长输出仍可浏览、选择和搜索。
- 窗口或侧栏拖动会每帧调用 fit，让 xterm 反复重排全部历史。达到 10,000
  行后，连续几何变化等待稳定 100 ms 再拟合一次；强制连接/恢复布局仍立即执行。
- 修正补全、Tab 跟踪和换行判断的缓冲区坐标：读取 `baseY + cursorY`，避免
  产生历史后继续读取缓冲区开头的旧行。

Windows / Electron 40 的一次同机对比（开发构建，诊断开启，真实 WebTerminal
和 mailbox、确定性模拟 shell 输出）如下。耗时会受机器和渲染环境影响：

| 场景                                   |                   修复前 |            修复后的一次记录 |
| -------------------------------------- | -----------------------: | --------------------------: |
| 写入 50,000 行的附加行读取             |               200,220 次 |                      216 次 |
| 50,000 行容量填满后继续追加 10,000 行  |                 1,105 ms |                      409 ms |
| 一次 50,000 行搜索的行读取             |               509,388 次 |                  250,185 次 |
| 500,000 行搜索后的三次跳转额外行读取   |         每次重新扫描历史 |                        0 次 |
| 500,000 行 DOM 输入回显                | 隐藏窗口实测 472～883 ms |                     13.7 ms |
| 500,000 行搜索期间最大定时调度间隔     |           原路径同步扫描 | DOM 18.5 ms / WebGL 15.4 ms |
| 500,000 行容量填满后继续追加 10,000 行 |                        — |                      455 ms |

完整搜索的首轮扫描仍与历史量成正比；上述 500,000 行的完整计数约需
1.2～1.4 秒，其间会交还事件循环。后续跳转不再扫描历史。

调整字体、列宽或从 DOM 切换到 WebGL 时，xterm 仍必须同步重排一次已有历史。
CPU profile 确认，500,000 行时该次重排可能接近一秒。此次合并了连续拖动中的
重复重排；没有修改 xterm 的单元格存储和重排算法。测试分别记录渲染器切换
和稳定后的交互，避免把一次几何调整混入搜索或键盘回显测量。

复现命令和 CPU profile/JSON 指标路径见 [tests/README.md](../tests/README.md)。
回归覆盖两种渲染器、完整历史搜索、深处唯一匹配、中文选区、输入、容量溢出、
超长逻辑行、链接检测、任务取消、输出/尺寸变更后的索引更新和资源释放。

2026-10-22 继续排查了“持续大量输出时 SSH 断联”。已安装应用的日志中，
20:40:39 和 20:48:09 的断开均由客户端健康检查触发：等待心跳回复约 10 秒后
调用 `client.destroy()`，随后进入重连。日志定位了断开的触发点；本地真实
SSH 用例进一步复现了旧判断的误判机制。

SSH 全局请求的回复按 FIFO 排队，也与大量输出共享 TCP 传输。新增用例将
全局回复延后，同时继续发送终端数据；旧实现即使仍收到数据也会判定连接失效。
现在当前传输的新入站数据同样可以证明存活，并维护原生 keepalive 的状态。
尚未回包的探针会被复用，保留 FIFO 回调位置，避免重复检查积累探针或把迟到
回包交给端口转发等其他请求。取消、关闭、替换传输和清理时移除活动监听与
定时器。无入站数据且无回复时，仍保留原有超时检测；真实半开连接回归继续通过。

链路测试还复现并修复了两处问题：

- ssh2 1.17 的错误输出来自 `channel.stderr` 的 `data` 事件，原先注册的
  `extended data` 事件不会交付这些内容。现在读取真实 stderr 流，并将
  stdout/stderr 一起接入邮箱的暂停/恢复，避免共享 SSH 窗口被积压堵住。
- 终端按 32 Ki 字符分块时，可能切开 emoji 的 UTF-16 代理对，导致各块
  分别计算 UTF-8 长度时多确认字节。新增边界用例复现了 32,772 字节被确认
  为 32,774 字节；现在分块保留完整代理对，ACK 与实际输出字节一致。

新增真实 SSH 压测连续输出 510,000 行 stdout、160,000 行 stderr，包含
中文与 emoji，使用原生字节检测、主/渲染邮箱及 xterm 解析，每 100 ms 做健康
检查，写入前人为增加 2 ms 延迟以触发背压。校验包括原始内容哈希、渲染内容
哈希、ACK 总量、暂停/恢复、积压有界、50 万行历史容量与连接存活。IPC 桥接在
同一测试进程内执行，语法高亮使用恒等变换；实际 Electron 渲染和文件传输由
另外的终端回归覆盖。

2026-10-25 排查持续大量输出的吞吐。此前的 SSH 压测用恒等变换代替语法高亮，
主进程高亮的实际开销没有进入测量。按 16 KiB 分段（与 SSH 输出批次一致）
在 Node 24 下单独测量主进程输出处理：

| 输出类型                 |                     修复前 |    修复后 |
| ------------------------ | -------------------------: | --------: |
| 带时间戳/IP/路径的日志行 |                   6.1 MB/s | 16.0 MB/s |
| `seq` 数字               |                  14.6 MB/s | 23.7 MB/s |
| 彩色 `ls`                |                  17.5 MB/s | 20.3 MB/s |
| 无换行的长 JSON          | 7.7 MB/s，随行长二次方变慢 | 23.2 MB/s |
| hexdump                  |                   6.8 MB/s | 20.9 MB/s |

- 高亮区间去重对每个候选检查全部已选区间。日志输出每 2 MB 约有 16 万个候选，
  去重耗时超过全部正则匹配。现在已选区间保持有序，二分定位后只检查相邻两个。
- 远程命令提取把未换行的输出不断拼接并重新切分：无换行输出 2/4/8 MB 分别
  耗时 43/152/589 ms，缓冲区也无上限。提取结果没有任何读取方，只写一条
  INFO 日志，已删除。编辑器检测只在状态变化时记录日志，不再对每段含
  `more`/`cat` 的输出写日志。
- IPv6 规则在每个单词边界尝试全部分支，即使没有匹配也占全部正则耗时的一半。
  所有分支都以两个间隔不超过 4 位十六进制的冒号开头，现在先用前瞻排除；
  随机语料对比新旧正则匹配结果完全一致，该规则耗时降为约 1/4。

渲染端新增持续输出测量：每条约 16 KiB，未确认字节达到 512 KiB 时暂停，
与主进程背压一致；共写入 32 MiB。开发构建一次记录为 DOM 27.7 MB/s、
WebGL 40.2 MB/s，最大定时调度间隔 40 ms / 130 ms。隐藏窗口的动画帧被节流，
因此不统计帧率。CPU profile 中主要是 xterm 解析；xterm 滚动条每次滚动重设
自动隐藏定时器，约占 8%。开发/诊断模式的历史字节统计原先对每行切片并编码
两次，约占 15%，现在原地计数；生产构建不创建该统计器。

500,000 行、123 列时，xterm 的行单元格数据约 704 MB（每格 12 字节，与实际
文本长度无关），默认 50,000 行约为其十分之一。多个标签页都使用最大容量时，
内存占用会按标签页数量成倍增加。
